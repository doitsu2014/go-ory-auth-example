# Implementation Plan — Pseudonymous customer login identifiers

## Approach

Build the walking skeleton U1→U7 first (Go service + Kratos/compose), then
U8 migration, then clients (U9, U10), then docs (U11). Integration tests
(U12) run in Launch against the local stack.

Branch: current worktree branch `doitsu2014/sandworm` (short-lived, PR to
`main`, links intent `261004-pseudonymize-customer-login`). Commits are not
made by the agent unless asked.

## Conventions

- Hexagonal layering (`domain ← app ← adapter ← cmd/platform`), sqlc for SQL,
  goose forward-only migrations, oapi-codegen strict server, RFC 9457.
- Comment density and naming follow the surrounding files (requirement ids in
  comments, e.g. `// PLI-FR-05`).
- No address, pseudonym, code or ciphertext in any log line or error string.
- Generated code (oapi, sqlc, admin-web `schema.d.ts`, Flutter l10n) is
  regenerated by tools, never hand-edited, and committed.

checkout. Integration runs in Launch will use it only after confirming it is
this worktree's stack; otherwise a separate compose project name is used so
the running one is not disturbed.
