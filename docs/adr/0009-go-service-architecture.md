# 0009. Hexagonal Go service: chi, pgx + sqlc, goose, oapi-codegen

- Status: Proposed
- Date: 2026-10-03

## Context

The Go service integrates three external systems (Kratos, Keto, PostgreSQL)
whose deployment may change (self-hosted ↔ Ory Network). Business rules must be
testable without them.

## Decision

- Ports & adapters layout (`domain` ← `app` ← `adapter`), enforced by `depguard`.
- `chi` router; HTTP layer generated by `oapi-codegen` strict server.
- `pgx/v5` + `pgxpool`; `sqlc` for typed queries; `goose` SQL migrations.
- `slog` logging, OpenTelemetry tracing/metrics, `cobra` CLI.

Details: [Go backend guidelines](../principles/02-backend-go.md).

## Alternatives considered

- **Gin / Echo / Fiber** — popular; chi stays closest to `net/http`.
- **GORM / Ent** — faster CRUD scaffolding, but hides SQL; schema is small and
  sqlc keeps queries explicit.
- **golang-migrate / Atlas** — both fine; goose chosen for SQL-file simplicity and embedding.
- **Flat package layout** — less ceremony, but couples domain to Ory SDK types.

## Consequences

- Slightly more boilerplate (ports, mappers) in exchange for testability and
  replaceable integrations.
- Generated code must be kept in sync (CI check).

## Revisit when

The service grows into multiple bounded contexts → split modules or services.
